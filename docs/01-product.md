# 01｜产品需求与范围

## 目的与使用上下文
用户不想先成为目的地专家，也不想先填写完整预算问卷。工具应代做资料研究，再帮助用户形成选择。最重要的体验不是长文输出，而是“先看到可比较的大致攻略，之后可反复调整，且每次调整有依据”。

## 需求编号
| ID | 必须实现的行为 | 验收关注 |
|---|---|---|
| R01 | 仅给出出发地、目的区域和模糊假期也能开始 | 不要求先补齐预算/交通 |
| R02 | 首轮给 2～3 个有差异的大致路线，证据不足时允许更少并解释 | 地区、看点、天数范围、取舍、假设 |
| R03 | 每轮最多提出 1～2 个关键决策问题，附建议和比较 | “没想好”不是错误 |
| R04 | 自动搜索并读取相关小红书攻略 | 摘要与正文分开，失败透明 |
| R05 | 普通用户通过 UI 完成正常登录，复用自己的本地会话 | 不手填 Cookie、不看终端 |
| R06 | 小红书访问有预算、去重、串行调度和暂停恢复 | 拒绝访问后不继续搜索 |
| R07 | 大方向确定后再展开具体活动和住宿 | 不首轮铺满景点/酒店 |
| R08 | AC→ABD 可修改，锁定项保留，版本可恢复 | 时间、路线、费用差异 |
| R09 | 使用高德做地图和路径依据 | 没有地图数据不虚构路程 |
| R10 | 交通、住宿、吃喝、活动费用统一口径 | 估算、报价、未知、已付分开 |
| R11 | 允许保存的研究成果进入个人 RAG | 来源、时效、删除传播 |
| R12 | 任务重启可恢复，旧任务不能覆盖新选择 | 版本号与操作记录 |

| R14 | 发布版无需用户安装开发环境 | Windows 干净环境验收 |

## 主要故事
S1：输入“我国庆节想从成都去川西玩”。先研究路线组合，不把年份、假期全长、预算、人数或自驾设成用户已确认事实。可以提出明确标为暂定的天数区间。

S2：选择一个方向后说“5 天，不知道怎么去”。先给每日片区轮廓，再比较驾驶/非驾驶；问人数和驾驶意愿。若无法取得对应交通信息，保留方案假设。

S3：用户说“预算没想好”。先说明依据和费用缺口；人数未知时不能给伪精确的两人全程总价，可提供明确单位的参考项或先询问人数。

S4：选择 A、C 后改 A、B、D。先展示新版本的可行性与差异，不立即覆盖用户确认版。已锁定酒店或返程时间不得悄悄改变。

S5：小红书出现登录验证。暂停所有该账号研究任务，保留已有资料与选择，引导在官方页面处理；恢复后只续做未完成部分。

## 三个交付等级
- **D0 离线演示**：全 mock，无真实源。常驻“合成演示”标识，仅验证交互和计算。
- **D1 小红书研究预览版**：真实登录、有限研究和粗略攻略达到门禁；地图/报价可仍显示未配置。这不是完整旅行工具发布。
- **D2 v0.1 完整个人版**：D1＋多轮具体安排＋高德实际接通＋预算状态完整＋资料复用＋本地发行包。票价通道未接入时，对应类别明确未知；不能声称全量实时比价。

## 不在首版
多人云服务、跨用户共享小红书全文/向量集、酒店机票自动购买、评论采集、视频转录、用户主页遍历、推荐流挖掘、自动收藏点赞、验证码代解、手机独立浏览器自动化、全国路线覆盖率承诺。

“开源而非商用”在这里首先指免费公开本项目代码、不建设商业托管服务；是否禁止他人商业使用需另定许可证，不能自动写成矛盾的许可条款。详见 09。

## 首次设置的体验预算（设计目标，待实测）
应用启动后，普通用户完成：模型配置一次 → 小红书连接一次 → 输入需求。小红书正常路径不超过“连接、扫码、官方确认”三个主要动作；平台额外验证不在本应用能消除的范围内。模型和地图 key 用表单校验及帮助入口引导，不要求改配置文件。

## 可用性与准确性
宁可输出少一个选项和清楚的缺口，也不为了固定凑够三个路线虚构资料。主观体验应归属于来源；报价与时间约束由对应来源和程序支持。节假日道路、预约等动态条件未核实时明确风险，不将历史笔记表述为当前保证。
